## Planned fixture and evidence setup

Reset to the original seed before independent variants, especially edits, cancellations, deletions, restores and sync conflicts. For output branches capture the generated artifact or intercepted arguments, never send a message or invoke a real printer. For sync substitute in-process responses at the transport boundary; assert attempted calls and their order without contacting an endpoint. Stop if isolation cannot be verified.

### PO Save and Edit (NOT RUN)

- **L07-02 (paste versus manual quantity):** With supplier, date and item set, compare a negative order quantity in the paste and manual entry paths. The paste parser skips a row unless `qty > 0`; the manual input passes through the entered value, and Save tests `li.item && (+li.ordered)`. A named negative-quantity line therefore passes Save and persists as negative, while zero or nonnumeric quantities are filtered out. A negative-only order has no remaining quantity and derives **Completed** without receiving anything. This is a source discrepancy, not an approved validation rule (L6252-6275, L6485-6492, L6693-6699, L6713-6764).
- **L08-04 (first exact historical match):** The draft is a copy, but Save reads historical `received` and `cancelled` from the first exact, case-sensitive item-name match in the stored PO, not from the draft totals or the product ID. On a synthetic save-handler fixture, seed prior same-name lines with different product IDs and totals, then save two retained rows with that name. Both take the first prior row's totals, even when their IDs differ; reversing the stored line order changes which totals both inherit. A case-changed name with the same ID takes neither. Inspect raw saved lines for duplicated or lost cumulative quantities; dated receipt logs are not copied (L6521-6532, L6735-6764).
- **L08-04 (reachability control):** Add the same product on separate rows of a new PO and confirm both are retained by Save; Add Item and the save map do not deduplicate them. That does not establish reachability of the historical carry-forward fixture: normal PO list Edit is Pending-only, and a valid PO with receipts is Partially Received or Completed. Order Planner opens the form with a new ID, not an existing received order. Keep the received duplicate-history branch synthetic-only (L6267-6275, L6330-6341, L6637-6644, L6745-6764, L10546-10575).

### PO Status and Purchase Value (NOT RUN)

- **L07-03/L08-03 (status versus quantities):** Compare a fresh Pending order, a partially received order, and a fresh order closed without receiving anything. `poRemaining()` clamps each line's `ordered - received - cancelled` at zero before summing; an overfilled line cannot offset another line's open quantity. With no PO-level flag, zero remaining means **Completed**, even when nothing was received. With positive remaining, any positive total received or line-cancelled quantity means **Partially Received**; otherwise it is **Pending**. Close Remaining changes line quantities, not `po.cancelled`. On a separate synthetic copy, set the PO-level flag and leave positive remaining and existing receipts: the list and View display **Cancelled** even with quantity left. Both Completed and Cancelled are excluded from Open POs and suppress Receive, but the flag alone does not remove receipts from purchase value, on-hand or FIFO. No PO-level Cancel action was found in the traced list/detail/receive paths; use the seeded flag to test this branch (L1090-1100, L1198-1214, L6252-6275, L6305-6367, L6848-6873, L7007-7021, L8884-8892, L10374-10386).
- **L08-01/L08-04 (purchase value versus stock):** For the same matched supplier and item, compare a line with complete dated receipts at different rates, the same cumulative quantity with an empty or absent receipt log, and the incomplete-log variant from L11-04. `liBought()` sums receipt quantity times receipt rate when the array is nonempty, using the current line rate for a zero or otherwise falsy numeric receipt rate. Only an empty or absent log uses cumulative `received × line rate`; a partial log does not add any unlogged remainder. Check Supplier-wise Purchases and the Suppliers totals, which add positive PO values without a PO status or receipt-date filter. In the partial-log variant, purchase value reflects only the logged quantity, on-hand still uses cumulative received quantity, and FIFO values only the remaining layers from positive logged quantities. The cumulative-only control instead supplies one lot dated to the PO when that date is present. Compare all three independently; FIFO is not a second purchase total (L1065-1075, L1090-1100, L1129-1148, L1198-1222, L1308-1337, L6255-6265, L8884-8901, L10374-10386).
- **L08-06 (rate fallback divergence):** Keep the existing PO line rate positive; compare a zero-rate receipt with a negative-rate receipt. Zero falls back to the line rate for purchase value and FIFO. A negative rate is truthy and contributes a negative amount to `liBought()`, but FIFO requires a positive receipt rate and uses the positive line rate instead. Both receipts still increase on-hand by the received quantity, and a nonpositive PO purchase total is omitted by the supplier aggregations. This is a candidate-source discrepancy, not an approved correction (L1198-1219, L6255-6265, L7024-7044, L8884-8892, L10374-10386).
