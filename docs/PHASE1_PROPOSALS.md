# Phase 1 proposals

**Status: Unapproved, discovery only.** This note supports the Phase 1 exit criteria in [PRD.md](PRD.md). It doesn't authorize implementation, access, or cutover, and doesn't change [OPEN.md](OPEN.md) or [DECISIONS.md](DECISIONS.md). The supplied HTML remains an unchanged candidate, not a verified deployed baseline. Runtime behavior and live metadata are unverified. The boundaries below describe proposed responsibilities, not deployed tables, interfaces, or source precedence.

## Rust, Supabase, and SQLite (R-1, R-2, R-4, R-7; DEC-004, DEC-006)

| Layer | Recommended responsibility |
| --- | --- |
| Presentation | Render the full ERP and pass typed input to Rust. Keep platform adapters for installation, image sharing, print, and PDF separate from calculations and authorization. Android tablet is a full client, not a companion. No retained JavaScript business logic. |
| Shared Rust core | Model money, quantity, dates, identifiers, explicit rounding, workflows and previews, and build output from authorized records. Compare calculation and output fixtures with the frozen original, including historical edits, cancellations, partial receipts, GST, FIFO, crates, godown, udhaar and cash book. Local calculations are never authoritative for posting. |
| Hosted Supabase | The existing project is the proposed production authority under the PRD, not a declaration of historical source precedence. Recheck authorization and current state on the server; expose narrow reads and transactional business commands, not client writes to individual stock, invoice, or ledger records. Enforce posting invariants and compare committed results against Rust previews and legacy fixtures to catch rule drift. |
| Per-device SQLite | Persist provisional drafts and minimal authorized read projections. Keep posted data read-only locally, with freshness indicators. Resume projected changes from a server-issued checkpoint, applying revisions and removals with checkpoint progress in one local transaction. If a checkpoint or permission scope expires, rebuild the projection without replaying drafts. |

**Alternative:** Refresh the complete authorized projection on reconnect instead of maintaining an incremental feed. This is simpler to verify but can be slower and use more bandwidth; compare with measured volumes once evidence is available. Neither design needs a shop server or a second business entity. Select a presentation stack only after installed-platform workflow and output feasibility is demonstrated. OPEN-001 and OPEN-005 block baseline and target conclusions; OPEN-002 blocks tailoring the hosted boundary to the deployed system.

## Permissions, projections, and device lifecycle (R-5; DEC-007; OPEN-004)

The following is a **recommended starting matrix**, not an access grant. All permissions, including owner permissions, must be explicitly approved; unapproved operations stay denied. Scope staff records to the approved operational need, such as assigned location or shift only if the owner confirms those boundaries.

| Capability or data | Owner | Manager | Cashier |
| --- | --- | --- | --- |
| Provisional orders and online sale confirmation at reviewed terms | Allow | Allow within scope | Allow within scope; credit sales separately gated |
| Customer and invoice lookup, reprint or share | Allow | Scoped operational history and fields | Minimum billing lookup and permitted invoices only |
| Price, tax, stock or credit conflicts | Authorized review only; no bypass of hard constraints | Review specified conflicts only if delegated | Show permitted differences; route exceptions, no override |
| Posted bill edits and cancellations, udhaar receipts, cash-book actions | Allow as separate audited commands | Individually delegate by action and scope | Deny by default; explicitly review any shift receipt or cash-book need |
| Purchases, partial receipts, crates, stock adjustments and godown transfers | Allow | Delegate operational actions with cost-free inputs and outputs only; otherwise owner handles | Availability lookup only for billing; no stock mutations apart from authorized sale |
| Costs, FIFO valuation, margins, owner reports, raw exports and backup/restore | Owner-only via separately approved access and recovery workflow | Deny; separately approve any cost-free operational report or export | Deny; allow only approved billing outputs |
| Staff accounts, roles, device provisioning and business settings | Owner-controlled and audited | Deny unless separately approved for a named action | Deny |

**Alternative:** Reserve all exceptions and sensitive operational mutations for the owner rather than delegating to managers. This reduces exposure but can delay receipts, corrections and stale-order resolution. OPEN-004 must settle each action, field and row scope, approver, permitted device, and exception policy. Approval of an exception never bypasses validated tax rules, available stock, or other hard constraints.

**Projection and lifecycle recommendation.** Check individual accounts and current permissions in Supabase using restrictive grants, row policies where applicable, and explicit allowlists on reads and commands. Deny raw record access and serialize only approved fields, including in nested objects, errors, sync events, reports, exports and backups. Sale price and availability need not reveal acquisition cost, FIFO layers, margin, or owner reports; don't deliver those fields or aggregates that reconstruct them to staff devices. Keep raw snapshots and administrative credentials outside clients. Recommend distinct provisioned owner devices for owner-only data and no owner-data mode on staff devices.

Separate per-account caches, drafts, sync cursors and session credentials. Protect credentials with platform secure storage and scope local data protection to the account. On sign-out or account switch, stop sync, clear visible state and credentials, and lock the previous account's local data; never load it into the next account. On reconnect, check current role and device status before refresh or confirmation; on revocation or downgrade, block access immediately once known and purge disallowed projections, queued output and temporary files. A disconnected device can't receive a revocation, so recommend a bounded offline access window for provisioned staff, limited to drafts and the minimum cache they need. Consider no offline access on shared or unmanaged devices rather than accepting that exposure. Owner approval is needed for offline expiry, lost-device response, purge and retention rules, and whether to discard or securely recover drafts after account removal. Never transfer a draft by exposing the previous account's cache.

## Offline draft and online posting (R-6, R-7; DEC-008; OPEN-003, OPEN-004)

**Recommendation:** Give each draft a durable identity and revision. Save, reopen and edit it across restart, marked provisional, with cached terms labeled as estimates. A draft cannot take or record payment, reserve or decrement stock, release goods, or issue a final invoice. Reconnect refreshes authorized terms but never submits a sale. Online review should show old and current price, tax, stock availability and credit terms, subject to the projection. If terms changed, require review and a new explicit confirmation by someone authorized for the current terms. If the order cannot be fulfilled, block it rather than silently substituting terms. Bind confirmation to the reviewed revision and terms; revalidate inside the commit transaction even if the review just happened.

Persist a distinct request identity and its immutable confirmation intent before sending. In Supabase, scope the identity to the authorized caller and operation, bind it to canonical intent (draft identity, revision, lines and confirmed terms/payment intent), and store the committed outcome with the posting. An authorized identical retry returns the original invoice and outcome without creating effects; reuse with different intent is rejected. Keep that mapping for the supported recovery horizon and retain a durable duplicate-posting guard. After a timeout or restart, mark the attempt outcome unknown and offer authorized status lookup or explicit retry with the same identity; don't mint a replacement or edit and repost until the outcome is resolved. A definite stale rejection sends the user back to review; a newly confirmed intent gets a new identity. A retry after revocation must not expose a now-restricted result.

Use one transaction for validation, invoice allocation under verified rules, sale, stock and FIFO effects, payment or udhaar and ledger effects, and the recorded outcome. Recommend locking affected numbering and inventory/FIFO resources in a consistent order, with database uniqueness for the verified invoice series/period identity and the logical sale per draft, even across distinct request identities. Protect any shared credit limits against concurrent changes too. Re-read under the transaction's concurrency controls; a losing confirmation receives a conflict or requires fresh review, not a partial invoice or stock movement. Exact invoice allocation and failure behavior must follow verified rules, not assumptions about gaps or numbering scope. **Alternative:** Use serializable transactions with bounded retries and the same uniqueness guards; select based on hosted contention and failure evidence, with no retry silently accepting different terms. Automatic replay of drafts is excluded by the PRD.

## Migration, cutover, and rollback (R-8, R-10; DEC-009, DEC-010; OPEN-002, OPEN-003, OPEN-006, OPEN-007)

**Recommendation:** Stage and rehearse a repeatable import on approved protected copies in the separately authorized test project. Capture Supabase, Sheets and recurring JSON snapshots with custodian, capture time and cutoff, scope, method, digest and protected location. Map reads, writes, overlap and missing history by record type, including Sheets write behavior and each JSON export's coverage. Keep raw copies immutable and restrict access. Maintain an import manifest with input and mapping versions, source identifiers and target lineage, and a conflict log with affected records, evidence, disposition and signer. Quarantine unresolved mappings; don't infer precedence, flatten history, or silently merge or discard records. Stable identity mapping and repeat-import checks must show unchanged inputs produce no duplicates.

Reconcile record history and control totals: invoice identifiers, status, edits and cancellations, invoice series and the next number without issuing a live invoice, GST, payment and udhaar balances, cash book, stock by item/location, crates and godown, and FIFO lots and valuation. Trace linked effects and explain every difference; require no unexplained variance or missing in-scope records. **Alternative:** Stage historical imports early and apply a final delta only if evidence proves reliable change and deletion capture across all approved sources. Otherwise prefer reimport from the final frozen snapshots using the rehearsed process; earlier loads are rehearsal evidence, not the cutover baseline.

**Cutover:** After parity and rehearsal sign-off and separate written owner authorization, fence every legacy writer, including other devices, integrations and scheduled imports. Drain in-flight work and verify the pause before capturing the final protected snapshots. Keep the new path read-only until migration reconciliation, access checks and invoice continuity are signed by the owner and accounting signer. Enable only the new path, run the approved smoke procedure and reconcile any actual posting. Treat a committed smoke posting as a new write for rollback purposes.

| Rollback boundary | Recommended procedure and evidence required to reopen |
| --- | --- |
| Before any new authoritative write | Fence the new path and verify from server-side records and in-flight request resolution that nothing committed after the switch, not merely that no client saw success. Preserve attempted-operation evidence. Verify or restore the protected pre-switch state, reconcile it and the next invoice to the final legacy cutoff, and reopen legacy only with recorded rollback approval and the new path still fenced. |
| After any new authoritative write, or if commit status is uncertain | Fence both paths, resolve in-flight requests and capture protected checkpoints and all committed post-switch effects, including sales, corrections, invoice numbers, payments, credit, stock/FIFO and ledger movements. Preserve request and record identities and audit history. Rehearse a controlled transfer onto a copy of the frozen legacy state with an approved mapping and repeat-safe application. Compare record links, balances and control totals, and verify invoice continuity without reusing issued numbers. Reopen only after evidence that every new transaction is retained and reconciled, accounting sign-off and authorization by the named rollback authority. If faithful transfer can't be demonstrated, keep legacy read-only and pursue an approved forward repair or reconciliation plan; never reopen a stale legacy snapshot. |
